0002 — Failure is a value: Result and match

One concept: in Rust, failure is a value — a Result holding either success or error — and match forces you to handle both. No exceptions, no try/catch. One win: you can explain every line of the parse block in your own guessing game, including the line that silently decides what counts as a valid guess.

Bridge from home: you wrote lib-result, so you already know this shape — a container with two variants, Ok and Err. Rust's Result<T, E> is the same idea, with one difference that matters: the compiler refuses to let you ignore either variant.

1 · Recall first (no peeking)

Q1. In your TypeScript lib-result, a Result holds two possibilities. Name them.

Reveal

Ok (success value) and Err (error value). Rust uses exactly these names — the Book's guessing game matches on Ok(num) and Err(_), and so does your code.

Q2. Look at your guessing game: what happens when the player types -5? Guess before scrolling.

Reveal

It prints "Invalid guess". The reason is a single four-character annotation — : u32 — and §3 proves it by removing it.

2 · The knowledge (five minutes)

Here is your parse block, the whole lesson in eight lines (Book ch. 2, mirror):

let guess = match guess.parse() {
    Ok(num) => num,
    Err(_) => {
        println!("Invalid guess, enter a number between 1 and 100 or type 'quit' to exit");
        continue;
    }
};
  • parse() returns a Result, not a number. Like your lib-result, it holds either Ok(num) or Err(e). There is no throwing; the failure travels inside the value.
  • match opens the box — every variant gets an arm. Ok(num) binds the number; Err(_) catches every error, where _ is a catch-all meaning "I don't care what's inside" (the Book's words: it matches all Err values "no matter what information they have inside them"). The arm prints a message and continues the loop.
  • The second let guess shadows the first. Rust lets a new binding reuse a name, hiding the old one — the Book: "Shadowing lets us reuse the guess variable name rather than forcing us to create two unique variables, such as guess_str and guess." The String still exists underneath; the name now points at a number. (Full shadowing rules come with Chapter 3.)
  • Nothing says u32 near parse() — yet it produces one. Type inference flows backward: secret is annotated u32, so secret.cmp(&guess) demands guess be u32, so parse() must produce u32. The Book makes the same point in reverse: its draft compares a String against a number and dies with E0308: mismatched types — "Rust has a strong, static type system. However, it also has type inference." Your finished code is the fixed version of the Book's deliberate error.

3 · The compiler as teacher, then your own experiment

Step 1 — predict. This compiles or not? If not, what is the error and the fix?

let n = "42".parse().expect("bad");
Reveal after guessing

It fails. Nothing pins down what parse() should produce — no annotation, no later use — so inference gives up. The real output (reproduced locally, trimmed):

error[E0284]: type annotations needed
 --> src/main.rs:2:9
  |
2 |     let n = "42".parse().expect("bad");
  |         ^        ----- type must be known at this point
help: consider giving `n` an explicit type
  |
2 |     let n: /* Type */ = "42".parse().expect("bad");

The compiler doesn't just reject — it prescribes the fix. Read help: lines first; they are correct more often than not. (Modern rustc reports this as E0284; older texts say E0282. Same disease.)

Step 2 — reproduce it. In playground/, create examples/e0284.rs with that one line inside fn main, run cargo build --example e0284, and read the full error yourself. Then fix it with : u32, rebuild, and delete the file. Checkpoint: you saw E0284 with your own eyes and cleared it with an annotation.

Step 3 — the annotation is behavior. In guessing_game/src/main.rs, temporarily delete : u32 from let secret: u32. Predict: does it still compile? Then build and run printf -- "-5\nquit\n" | cargo run -q. Checkpoint: it does compile — integers silently fall back to i32 — and -5 is now accepted as a guess ("Bigger!") instead of rejected. The annotation wasn't documentation; it was the rule that kept negatives out. Revert the edit when done (git diff should be empty).

4 · Lock it in

.expect("…") on an Err value…

expect unwraps success or crashes with your message — fine for a tutorial's input loop, forbidden in library code (stage 2 replaces it with ? and real error types).

In Err(_), the underscore means…

_ is the catch-all: every Err matches regardless of contents. Your game deliberately discards why parsing failed.

guess.parse() knows to produce u32 because…

Inference flows backward from secret.cmp(&guess): secret is u32, so guess — and therefore parse()'s output — must be u32. (There is no default; unpinned integers fall back to i32, as Step 3 showed.)

Shadowing guess with a u32 gives you…

A shadow is a brand-new binding reusing the name — nothing is mutated or converted. (Mutation, mut, is next lesson's topic.)
